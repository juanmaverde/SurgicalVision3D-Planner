# SurgicalVision3D Planner Multi-Trajectory Array Spec

## 1. Purpose

This document defines the implementation plan for a new planning mode that derives
multiple applicator trajectories from one validated master trajectory.

The core idea is:

- the user defines exactly one master trajectory
- the module can generate a deterministic array of secondary trajectories around it
- all derived trajectories remain parallel to the master trajectory
- the array is defined by angular distribution around the master axis

Examples:

- `4` trajectories: `90 deg` spacing (`N`, `E`, `S`, `W`)
- `6` trajectories: `60 deg` spacing
- `8` trajectories: `45 deg` spacing

This feature should preserve the beginner workflow principle that one manually edited
trajectory remains the authoritative source of truth.

## 2. Scope

### In scope

- Add a planning mode switch: `Single` vs `MultiTrajectoryArray`
- Keep one master trajectory as the only user-authored trajectory
- Generate derived trajectories around the master axis using a deterministic angular rule
- Support configurable array size and radial offset
- Preview derived trajectories as line markups before applicator placement
- Place probes from the full generated bundle (`master + derived`)
- Reuse existing merge, margin, and coordination logic on the generated bundle

### Out of scope for first implementation

- Automatic optimization of offset/radius from tumor geometry
- Non-parallel child trajectories
- Child-specific manual editing
- Asymmetric custom child layouts
- Thermal or physics-based dose optimization
- Auto-pruning trajectories based on risk structures

## 3. User-Level Concept

The planner should expose two planning modes:

1. `Single trajectory`
2. `Multiple trajectories`

In `Multiple trajectories` mode:

- the user still creates one master trajectory
- the module generates an array around the master
- the user chooses how many derived directions exist around the master axis
- the user chooses the radial offset in mm

The generated array is always centered on the master.

Interpretation of `trajectory count`:

- `1` means master only
- `4` means master plus four child trajectories arranged every `90 deg`
- `6` means master plus six child trajectories arranged every `60 deg`
- `N` means master plus `N` child trajectories arranged every `360 / N deg`

This keeps the master trajectory clinically primary while allowing symmetric expansion.

## 4. Clinical Geometry Model

### 4.1 Definitions

- `Master trajectory`: the manually defined reference trajectory
- `Derived trajectory`: a trajectory generated by translating the master trajectory
  in a plane orthogonal to the master axis
- `Array radius`: the perpendicular distance between the master axis and each derived axis
- `Angular spacing`: `360 / derivedCount`

### 4.2 Parallelism rule

All derived trajectories must:

- keep the same direction vector as the master
- keep the same length as the master
- preserve entry-to-endpoint ordering consistently with module conventions

### 4.3 Symmetry rule

For derived count `N`, child trajectories are distributed on a circle around the master axis.

For child index `k`:

- angle = `2 * pi * k / N`
- child translation = `radius * (cos(angle) * basisU + sin(angle) * basisV)`

Where:

- `basisU` and `basisV` span the plane orthogonal to the master direction
- `basisU` is the zero-angle reference direction

## 5. Deterministic Reference Frame

The term `north/south/east/west` must not depend on the current slice view.
It must be derived in patient-space coordinates.

### 5.1 Proposed rule

Given master direction `d`:

1. Choose a preferred anatomical seed axis:
   - first try superior-inferior patient axis: `[0, 0, 1]`
   - if nearly parallel to `d`, fall back to anterior-posterior axis: `[0, 1, 0]`
   - if still nearly parallel, fall back to right-left axis: `[1, 0, 0]`
2. Project the chosen axis into the plane orthogonal to `d`
3. Normalize the result to create `basisU`
4. Compute `basisV = normalize(cross(d, basisU))`

Interpretation:

- `North` = `+basisU`
- `South` = `-basisU`
- `East` = `+basisV`
- `West` = `-basisV`

For counts other than `4`, only the zero-angle anchor is named; the rest are indexed by angle.

This makes the array deterministic and independent of viewer orientation.

## 6. Functional Requirements

### 6.1 Master trajectory remains authoritative

- The user edits only the master trajectory markup
- Derived trajectories are regenerated from the master whenever relevant settings change
- Derived trajectories must never silently drift from the master

### 6.2 Generated trajectories are non-destructive

- Derived trajectories must be stored separately from the master endpoints node
- Clearing derived outputs must not affect the master trajectory

### 6.3 Array parameters

The first version should support:

- `planningMode`: `Single`, `MultiTrajectoryArray`
- `derivedTrajectoryCount`: integer, default `4`
- `arrayRadiusMm`: float, default `10.0`
- `arrayAngleOffsetDeg`: float, default `0.0`
- `includeMasterInPlacement`: bool, default `True`

Optional later:

- ring count > 1
- per-ring radius
- staggered angular offset per ring

### 6.4 Supported trajectory arrays

Phase 1 must support a single circular ring.

Examples:

- `derivedTrajectoryCount = 4`: `0, 90, 180, 270`
- `derivedTrajectoryCount = 6`: `0, 60, 120, 180, 240, 300`
- `derivedTrajectoryCount = 8`: `0, 45, 90, 135, 180, 225, 270, 315`

## 8. Node Ownership and Scene Objects

### 8.1 Master node

The existing master endpoints markup node remains:

- editable
- user-facing
- authoritative

### 8.2 Generated preview node

Derived trajectory preview should live in module-owned line nodes:

- one `vtkMRMLMarkupsLineNode` per derived trajectory, or
- one grouped folder via subject hierarchy

Recommended first version:

- one line node per trajectory
- deterministic names:
  - `SV3D Master Trajectory`
  - `SV3D Derived Trajectory 01`
  - `SV3D Derived Trajectory 02`
  - ...

### 8.3 Generated bundle semantics

The generated placement bundle is not stored as manual endpoint fiducials.
Instead, it is reconstructed from:

- the master trajectory
- the array config

This avoids inconsistency between manually edited and generated points.

## 9. Geometry Algorithm

### 9.1 Inputs

- one master `ProbeTrajectory`
- derived count `N`
- radius `r`
- angle offset `theta0`

### 9.2 Basis generation

Compute:

- `d = normalize(master.directionVector)`
- `basisU` using projected patient-space axis
- `basisV = normalize(cross(d, basisU))`

### 9.3 Child trajectory generation

For each `k in [0, N-1]`:

- `theta = theta0 + (360 / N) * k`
- `offset = r * cos(theta) * basisU + r * sin(theta) * basisV`
- `childEntry = master.entryPointRAS + offset`
- `childTarget = master.targetPointRAS + offset`

Create:

- same direction as master
- same length as master
- role name:
  - for `N = 4`: `North`, `East`, `South`, `West`
  - otherwise: `Derived {k+1}`

### 9.4 Bundle composition

If `includeMasterTrajectoryInArray`:

- bundle = `[master] + children`

Else:

- bundle = `children`

## 10. Workflow Integration

### 10.1 Beginner workflow changes

Keep the first steps unchanged:

1. import case
2. segment structures
3. define master trajectory
4. validate master trajectory

Then split Step 5:

- `Single Applicator Plan`
- `Trajectory Array`

Suggested UI controls:

- `Planning mode` dropdown: `Single`, `MultiTrajectoryArray`
- `Derived count`
- `Radius (mm)`
- `Angle offset (deg)`
- `Include master`
- `Preview Array`
- `Clear Array`

### 10.2 Placement integration

`Place Probes` must use:

- single master trajectory in `Single` mode
- generated bundle in `MultiTrajectoryArray` mode

This should be implemented by a new helper:

```python
def _plannedTrajectoryBundle(self) -> list[ProbeTrajectory]:
    ...
```

Then route the following actions through it:

- place probes
- create trajectory lines
- evaluate coordination
- future bundle-level validation

### 10.3 Merge and margins

No conceptual change is required.

Existing functions already accept trajectory lists and generated probe lists.
The main change is which list is passed in.

## 11. Validation Rules

### 11.1 Master-first gating

The array can only be generated if:

- exactly one valid master trajectory exists
- master trajectory validation has been completed

### 11.2 Bundle validation

Phase 1 should add bundle-level checks:

- even though all children are parallel, they may intersect critical structures
- each child should be evaluated against the risk segmentation

Suggested output:

- bundle summary table with one row per trajectory
- fields:
  - `Role`
  - `AngleDeg`
  - `EntryPointRAS`
  - `TargetPointRAS`
  - `IntersectsCriticalStructures`
  - `MinDistanceToCriticalStructuresMm`

### 11.3 Coordination

Reuse the existing coordination pipeline.
This is already list-based and can operate on the generated bundle.

## 12. UI Specification

### 12.1 Phase 1 controls

- `Trajectory Array`

Fields:

- `Derived trajectories`

## 14. Owned Output Rules

Generated nodes must be module-owned and cleared when:

- master trajectory changes
- planning mode changes
- derived count changes
- radius changes
- angle offset changes
- geometry changes
- case is reloaded

This follows the current module policy for deterministic owned-output lifecycle.

## 17. Open Design Decisions

These need confirmation before coding Phase A:

1. Should `derivedTrajectoryCount` mean:
   - children only, or
   - total trajectories including master

This spec assumes `children only`.

2. Should `North` be anchored to patient superior, anterior, or screen up

This spec assumes patient-space deterministic anchoring.

3. Should bundle placement include master by default

This spec assumes `yes`.

4. Should invalid children be blocked from placement or just warned

This spec recommends:

- warn in Phase A
- optionally block in Phase C

## 18. Recommended Initial Defaults

- `planningMode = Single`
- `derivedTrajectoryCount = 4`
- `derivedTrajectoryRadiusMm = 10.0`
- `derivedTrajectoryAngleOffsetDeg = 0.0`
- `includeMasterTrajectoryInArray = True`

These defaults provide the first clinically intuitive pattern:

- one master trajectory
- one ring of four parallel children
- symmetric cross around the master
